## Part 1 — Code review (findings ranked by severity)

Severity = user impact + likelihood. Effort = S (≤1h) / M (a few hours) / L (a day+).

### 1. Every failure collapses into a generic HTTP 400 — HIGH · fix M

`server/api.ts:79-86` — the `wrap()` handler catches *all* errors and returns
`res.status(400).json({ error: e.message })`. There is no error taxonomy. A
missing Pandoc binary, a Puppeteer/Chromium crash, a malformed `book.yaml`, and
a genuinely bad request all arrive at the user as an indistinguishable 400 with
a raw internal message.

Concretely unhelpful surfaces:

- **Pandoc missing / wrong version.** `server/pipeline/exec.ts:21` — `run()`
  does `child.on("error", reject)`, so when `spawn("pandoc", …)` fails with
  `ENOENT` the promise **rejects** (it never reaches the exit-code branch in
  `runPandoc`). That raw `Error: spawn pandoc ENOENT` propagates verbatim to the
  400. The user sees a Node error string, not "Pandoc isn't installed / not on
  PATH."
- **Pandoc ran but failed.** `server/pipeline/pandoc.ts:41-47` — `runPandoc`
  throws `pandoc failed (exit N):\n<stderr>`. Better than nothing, but it's dumped
  straight into the 400 with no framing ("Your EPUB couldn't be generated by
  Pandoc — details below"), and stderr can be long/cryptic.
- **Chromium/Puppeteer crash.** `server/pipeline/render-pdf.ts:9-12` — the browser
  launch failure (missing Chromium download, sandbox failure) surfaces as
  whatever Puppeteer throws. `render-print.ts` and `render-pdf.ts` never
  distinguish "Chromium won't launch" from "the page threw during pagination."
  The README's own troubleshooting section says PDF errors trace back to an
  interrupted Puppeteer download — but nothing in the code says that to the user.
- **File I/O.** `ingest.ts` reports *missing* fonts/covers/matter as soft
  `warnings` (good, e.g. `ingest.ts:52,280,307,317,331`), but a genuinely
  unreadable `book.yaml` (permission error) or malformed YAML throws from
  `yaml.load` (`ingest.ts:246`) into the same 400.

**Fix.** Introduce a small tagged-error type and a classifier:

- Add an `AppError { code, userMessage, cause }` (codes like `PANDOC_MISSING`,
  `PANDOC_FAILED`, `CHROMIUM_LAUNCH`, `CHROMIUM_RENDER`, `BAD_CONFIG`,
  `IO_ERROR`, `BAD_REQUEST`).
- In `exec.ts:run`, detect `err.code === "ENOENT"` in the `error` handler and
  reject with a typed `PANDOC_MISSING`/`COMMAND_MISSING` error carrying the
  command name, instead of the raw spawn error.
- In `runPandoc` (`pandoc.ts`), wrap the non-zero exit as `PANDOC_FAILED` and
  keep the last ~40 lines of stderr as `detail`.
- In `getBrowser` (`render-pdf.ts`), wrap `puppeteer.launch` in try/catch and
  throw `CHROMIUM_LAUNCH` with the README hint ("re-run `npm install` to finish
  the Chromium download").
- In `wrap()` (`api.ts:79`), map `AppError.code` → HTTP status (400 for
  `BAD_REQUEST`/`BAD_CONFIG`, 422 for `PANDOC_FAILED`, 500/503 for
  `PANDOC_MISSING`/`CHROMIUM_LAUNCH`) and return
  `{ error, code, detail }` so the UI can show an actionable message. The web
  client already reads `.error` (`web/src/api.ts:3-14`); add `code`/`detail`.

This is the single highest-value change: it turns "it just says 400" into
diagnosable, self-serve errors that match the README's troubleshooting.

### 2. No Pandoc-presence / 3.x-version check at startup — HIGH · fix S

There is **no** startup verification that Pandoc exists or is version 3.x
(confirmed: the only `commandExists` call is for `java` in
`validate/epubcheck.ts:106`; `PANDOC` is just a bin name at
`pipeline/pandoc.ts:9`). The README (`README.md:24,366`) states Pandoc **3.x is
required** and that PDF/EPUB errors trace back to a missing/old Pandoc. Today
the user only discovers this on their first export, as the opaque 400 from
finding #1.

**Fix (where).** Add an async preflight in `server/index.ts` before/just after
`app.listen` (or a `/api/health` enrichment in `api.ts:107`):

- Run `pandoc --version` via `exec.run`. If it fails → log a clear banner
  ("Pandoc not found on PATH. Install Pandoc 3.x — https://pandoc.org") and
  expose the status in `/api/health` so the UI can show a startup warning.
- Parse the first line (`pandoc 3.x.y`) and warn if major < 3.
- Keep it non-fatal (still boot, since HTML preview via Pandoc will also fail
  loudly, but DOCX/EPUB clearly depend on it). Optionally also probe the
  bundled Chromium here so both external deps are checked in one place.

Effort is small: one `run()` call + a regex + a health field.

### 3. Zero automated tests — HIGH · fix M

There is no test runner, no test files, and no `test` script (`package.json:9-16`
has only `dev`/`build`/`start`/`typecheck`). Every change to the pipeline is
validated by hand. For a tool whose whole value is "the export is correct and
retailer-safe," this is the biggest structural risk.

**What `validate/epubcheck.ts` actually covers (so tests don't duplicate it):**
It is a *runtime* EPUB validator invoked during export, not a test suite. When
a real EPUBCheck jar + Java are present (`vendor/epubcheck/epubcheck.jar`,
`epubcheck.ts:87-101,104-117`) it shells out to the official validator and maps
its JSON messages. Otherwise it runs `builtinCheck` (`epubcheck.ts:44-85`),
which only asserts: `mimetype` exists and equals `application/epub+zip`;
`META-INF/container.xml` present; an `.opf` exists and contains `<dc:title>`,
`<dc:language>`, `<dc:identifier>`; a cover is declared (warning); nav.xhtml
present (warning); NCX present (info). It does **not** check spine order, TOC
correctness, subtitle metadata, per-section content, or that the requested
chapters/front matter actually made it in. So there is real coverage of gross
OPF/mimetype validity but **none** of structural fidelity.

**Recommended minimal golden-file suite** (add `vitest` as a devDep + a
`"test": "vitest run"` script):

1. **Fixture.** A tiny book folder under `server/__fixtures__/mini-book/` — a
   `book.yaml` (title, subtitle, author, series, one theme), one `frontmatter`
   file, two 3-line chapters, one `backmatter` file. Reuse `samples/` shape.
2. **EPUB golden.** `renderEpub(book, "universal")` → unzip the buffer (yauzl is
   already a dep) and assert: OPF contains `<dc:title>`, `<dc:creator>`,
   `<dc:language>`, `<dc:identifier>`; the spine lists title → copyright → nav →
   chapters in that order (locks in the `reorderToc` logic at
   `render-epub.ts:23-51`); each chapter title appears in a content doc; run the
   built-in `validateEpub` and assert `valid === true`. Snapshot the OPF (or a
   normalized subset) as the golden file.
3. **Print-PDF golden.** `renderPrintPdf(book, DEFAULT_PRINT)` → assert the
   returned `meta.pages > 0` and `meta.gutter` matches the KDP band for that page
   count (`autoGutter` in `print.ts`); assert the buffer starts with `%PDF`.
   (Full pixel-diffing is L-effort and out of scope for "minimal"; asserting page
   count + gutter + PDF magic bytes catches the common regressions — wrong trim,
   double-pagination, gutter band errors.)
4. **Pure-function unit tests** (fast, no Pandoc/Chromium): `cleanSeriesIndex`,
   `slugify`/`uniqueId`, `splitOnH1`, `buildTitlePage` (assert subtitle line),
   `assembleMarkdown` header attrs, `insertPrintToc` placement,
   `reorderSpineToc`. These need no external binaries and give the fastest CI.

Gate #2/#3 behind a "pandoc + chromium available" check so CI without the
binaries still runs the unit tier.

### 4. `render-pdf.ts` reading-PDF trim is hardcoded 6×9 — MEDIUM · fix S

`server/pipeline/render-pdf.ts:33-38` — the reading PDF is fixed at
`width: "6in", height: "9in"` with hardcoded margins. This is documented as a
"quick proof" PDF (README `:294`), so it's minor, but a 5×8 or Letter book's
reading PDF will be laid out at the wrong size. Fix: derive width/height from the
book's chosen trim (or expose a param) — S, and it reuses `getTrim` from
`print.ts`.

### 5. Robustness assumptions worth hardening — MEDIUM/LOW

- **Hardcoded ports 4242 / 5173.** `server/index.ts:10` reads `PORT` from env
  (good, defaults 4242) but `vite.config.ts:11-15` hardcodes `5173` and proxies
  to a hardcoded `http://localhost:4242`. If `PORT` is overridden, the dev proxy
  breaks silently. Also there's **no EADDRINUSE handling** on `app.listen`
  (`index.ts:25`) — if 4242 is taken the process throws an unhandled error. Fix:
  catch `listen` errors with a friendly "port in use" message; make the Vite
  proxy target read from an env var. (LOW · S)
- **Pandoc-in-PATH** — covered by #2.
- **Puppeteer/Chromium download** — `getBrowser` (`render-pdf.ts:9-12`) assumes
  the bundled Chromium downloaded successfully at `npm install`. No preflight, no
  friendly error (see #1/#2). The browser is launched with `--no-sandbox`
  (`render-pdf.ts:11`) unconditionally — fine for a local single-user tool, worth
  a comment noting it's deliberate. (MEDIUM, folded into #1/#2)
- **Global singleton browser** (`render-pdf.ts:6`) is never closed on process
  exit (`closeBrowser` exists but is unused in `index.ts`). Long-running dev
  sessions leak a Chromium; add a `process.on("SIGINT"/"SIGTERM")` → `closeBrowser`.
  (LOW · S)
- **`makeTempDir` cleanup on crash.** Pandoc/EPUB temp dirs are cleaned in
  `finally` (`render-epub.ts:115`, `render-html.ts:40`), but a hard crash leaks
  `os.tmpdir()/book-formatter/*`. Minor. (LOW)

## Subtitle support — design

**Current state: subtitle is *partially* implemented already.** It exists in the
model and renders on the title page, but is missing from ebook/print *metadata*
and is only half-styled. Tracing the flow:

- **Model** — `BookMeta.subtitle?: string` already exists
  (`server/pipeline/types.ts:8`); ingested and trimmed at
  `server/pipeline/ingest.ts:78` (`subtitle: cfg.subtitle?.trim() || undefined`);
  read from `book.yaml` via `RawConfig.subtitle` (`ingest.ts:23`).
- **book.yaml** — round-trips through `saveMeta` (`server/matter.ts:238`,
  `setOrDelete(cfg, "subtitle", …)`) and `ensureConfig` (`matter.ts:107`). The
  sample sets `subtitle: A Novel` (`samples/clockwork-garden/book.yaml:9`).
- **Title page** — `buildTitlePage` **already emits** the subtitle:
  `ingest.ts:117` pushes `<p class="tp-subtitle">…</p>`. Styled in
  `themes/base.css:148-152` (`.tp-subtitle`).
- **UI** — `MetadataForm.tsx:82` already has a Subtitle field bound to
  `meta.subtitle`.
- **Compiled Markdown** — already writes `subtitle:` into the front-matter
  header (`render-markdown.ts:8`) and italicizes it under the H1
  (`build-doc.ts:92`, `assembleCleanMarkdown`).

**So what's actually missing** (the real work):

1. **EPUB OPF metadata.** `buildPandocMeta` (`server/pipeline/build-doc.ts:107-128`)
   sets only `title: m.title` — the subtitle never reaches the OPF. The clean
   EPUB 3 convention is a *title refinement*: a `dc:title` with
   `<meta refines="#title" property="title-type">main</meta>` plus a second
   `dc:title` with `title-type` = `subtitle`. Pandoc supports structured
   `title:` metadata (`type: main` / `type: subtitle`).
2. **Reading-PDF / DOCX metadata.** Same `buildPandocMeta` gap — subtitle isn't
   in the DOCX core properties or the PDF. (Title-page rendering is separate and
   already works via the generated `titlepage` section.)
3. **Per-theme title-page styling.** `.tp-subtitle` is styled **only** in
   `themes/base.css:148`. `classic` and `modern` restyle `.tp-author`
   (`classic/theme.css:28`, `modern/theme.css:34`) but leave the subtitle at the
   base italic — decorative gets no subtitle treatment at all. A subtitle should
   be a first-class, per-theme element like the author line.
4. **Print title page.** Uses the same generated `titlepage` section, so the
   subtitle already appears; only the per-theme CSS (`print-base.css:52` block)
   and possibly a `.tp-subtitle` size in each theme's `print.css` need a look.

**Design.**

- Change `buildPandocMeta` (`build-doc.ts`) to emit structured title metadata
  when `m.subtitle` is set:
  ```yaml
  title:
    - type: main
      text: <title>
    - type: subtitle
      text: <subtitle>
  ```
  This gives Pandoc the correct `dc:title` refinements for EPUB and carries the
  subtitle into DOCX/PDF. Keep the plain-string form when no subtitle (avoid
  churn / regressions in the golden OPF).
- Add per-theme `.tp-subtitle` rules to `themes/classic/theme.css`,
  `modern/theme.css`, and `decorative/theme.css` (size/case to match each
  theme's title treatment), and a print variant in each theme's `print.css` if
  present. Keep the base rule as the fallback.
- No model/UI/ingest/matter changes needed — those already handle subtitle.

**Files that change:** `server/pipeline/build-doc.ts` (metadata — the core
change); `themes/classic/theme.css`, `themes/modern/theme.css`,
`themes/decorative/theme.css` (+ their `print.css` where present); optionally a
golden-test assertion (see Part 1 #3) that the OPF now contains a `subtitle`
title-type refinement. **No changes** required to `types.ts`, `ingest.ts`,
`matter.ts`, `MetadataForm.tsx`, or `render-markdown.ts` — they already support
it. This is the load-bearing correction: the feature is 70% built; the gap is
metadata + per-theme CSS, not the model.

## Theming — design

### Does saving custom themes already exist? No.

Confirmed by tracing all three surfaces:

- **`server/pipeline/themes.ts`** — `THEMES` is a **hardcoded record** of exactly
  three configs (`themes.ts:11-33`); `themeList()` returns `Object.values(THEMES)`
  (`themes.ts:39-41`). There is no create/read/write of user themes.
- **Type system** — `ThemeName = "classic" | "modern" | "decorative"` is a closed
  union (`server/pipeline/types.ts:3`); `ingest.ts:75` and `getTheme`
  (`themes.ts:35`) both fall back to `"classic"` for anything not in the enum, so
  an unknown theme name is silently discarded.
- **`server/api.ts`** — `GET /api/themes` just returns the built-ins
  (`api.ts:108`). There is **no** POST/PUT/DELETE theme route. The only
  persistence is `saveTypography` (`api.ts:184`, `matter.ts:214`), which writes a
  per-book `typography:` block to that book's `book.yaml` — **not** a reusable,
  named theme.
- **Web** — `ThemePicker.tsx` only *selects* among `props.themes`; it cannot
  create or save one. `TypographyPanel.tsx` edits per-book overrides and saves
  them to `book.yaml` (`TypographyPanel.tsx:97-108`), again per-book, not a shared
  theme. CSS themes live as static folders under `themes/` (`paths.ts:8,14-25`).

So today's "theming" = pick 1 of 3 fixed CSS themes + per-book typography
overrides. Nothing reusable is saved.

### Recommended path: (c) saved custom themes, built on the typography layer that already exists.

Rationale. (a) "more built-in themes" is low-leverage and doesn't address the
roadmap ask ("custom theme editor"). (b) "more exposed typography controls" is
worthwhile but the `Typography` model (`types.ts:61-69`) + `TypographyPanel`
already expose body/heading font, drop caps, ornament, and chapter-title
size/case/align/style — the controls mostly exist; the missing piece is that
they're trapped per-book. (c) turns the *already-working* typography-override
mechanism into named, reusable, persisted themes — the highest-value, lowest-new-
surface path, and it's exactly the roadmap item. It also composes with the more-
controls idea: add controls to the same panel over time.

**Concrete design (a "saved theme" = base CSS theme + a saved Typography preset).**

- **Where themes live.** A user-themes directory outside the repo, e.g.
  `<userData>/book-formatter/themes/*.json` (mirror the existing
  `os.tmpdir()/book-formatter` convention in `paths.ts:30`; add
  `USER_THEMES_DIR`). Each file:
  ```json
  {
    "id": "my-cozy",
    "label": "My Cozy",
    "base": "decorative",          // one of the built-in CSS themes
    "typography": { … Typography … } // the existing override shape
  }
  ```
  Reusing the built-in CSS as a `base` avoids letting users author raw CSS
  (safer, no injection surface) while still giving real visual variety through
  the typography layer that already renders everywhere.
- **How persisted.** JSON files (human-editable, git-ignorable, portable). Add
  a small `server/pipeline/user-themes.ts` with `listUserThemes()`,
  `saveUserTheme()`, `deleteUserTheme()`. `themeList()` (`themes.ts:39`) merges
  built-ins + user themes; `getTheme` resolves a user theme to its `base`
  `ThemeConfig` and layers its `typography` in `buildPandocMeta` /
  `buildDocCss`. Loosen `ThemeName`/theme resolution so an unknown id maps to a
  saved theme instead of silently falling back to classic (`ingest.ts:75`,
  `themes.ts:35`).
- **Minimal UI.** In the existing `TypographyPanel`, add a "Save as theme…"
  button (name → POST `/api/themes`) and let `ThemePicker` list saved themes in
  a second group with a delete (✕). No new panels; it reuses the components that
  already exist. Selecting a saved theme loads its base + typography into the
  live preview through the current preview path (`api.ts:252`).
- **API additions.** `POST /api/themes` (save), `DELETE /api/themes/:id`
  (remove). `GET /api/themes` already exists and would now return the merged
  list.

**Why this is the right scope.** It ships the roadmap's "custom theme editor" as
a thin layer over the `Typography` override engine that's already wired end-to-
end (model → `book.yaml` → `buildDocCss`/`buildPandocMeta` → preview + every
export). It adds two API routes, one server module, one persistence dir, and two
small UI affordances — no CSS-authoring/injection risk, and it composes with
gradually exposing more typography controls later.

**Files that would change (design only, not built):**
`server/pipeline/themes.ts` (merge user themes into `themeList`/`getTheme`),
`server/pipeline/types.ts` (relax `ThemeName` / add a `UserTheme` type),
`server/pipeline/paths.ts` (add `USER_THEMES_DIR`), new
`server/pipeline/user-themes.ts`, `server/api.ts` (POST/DELETE routes),
`web/src/components/ThemePicker.tsx` + `TypographyPanel.tsx` + `web/src/api.ts`
(save/delete + merged list), and `ingest.ts` theme resolution.
